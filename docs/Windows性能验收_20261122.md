## 四、瓶颈定位（基于直测，非残差）

规模 1000 条件下完整 recall ≈1700ms 的构成：

1. **词面扫描/合并/重排的计算成本（首要，占 ≈70~90%）**
   - memory：编码 117ms + 存储 3ms + 词面拉取 1ms ≈ 121ms 直测，其余 ≈1530ms 为
     词面扫描 `lexical_hits`、`merge_items`、`rerank_and_filter` 等纯计算。
   - **重要修正**：此前把「词面补召全量拉取」列为瓶颈；实测拉取在 memory 后端仅
     **1.3ms**（规模 1000），真正昂贵的是候选集上的 O(N×M) 词面扫描与重排。

2. **存储后端的标量查询往返（milvus-lite 特有）**
   - 词面补召拉取：memory 1.3ms vs **milvus-lite 261.7ms**（约 200 倍）——进程内
     gRPC 往返开销；该路径在 recall 中会额外触发一次标量 query。

3. **CPU 语义编码（次要）**
   - 编码 P50 约 104~117ms；4 线程并发争抢使 P95 放大至 7.8s（memory）/12.9s（milvus）。

**差距如实呈现，未改金标、未放宽断言。**

## 五、优化建议（属 core / embedding 模块，建议另开任务）

- 词面扫描：候选集上限、倒排/索引化、或按 need 才走词面（当前 knowledge 意图即触发）
- milvus 后端：词面补召复用向量检索结果，避免二次标量 query；或缓存标量结果
- 编码：查询侧缓存、批处理、GPU 或轻量蒸馏模型；并发下编码串行化避免争抢

## 六、附带修复（实测发现的产品级 bug）

`MilvusClient._ensure_collection`：**已存在的集合不 load**——milvus-lite 及任何
重启后的 Milvus 集合处于 released 状态，直接 search 报 `code=101`。修复为存在时
也 `load_collection`（幂等）。持久化重启验证在新进程下 PASS（修复前必现崩溃）。

## 七、缺测与边界

- chat 耗时：模型服务不可用（503），**缺测单列**
- 无 GPU；`memory` 后端为进程内对照，不代表产品部署形态
- hash 接线干跑（`hash_wiring_dry_run.json`）仅验证链路，**不给达标判定**
- 重排合并与其他阶段为残差估算（见上表脚注）
- 复现命令见 WINDOWS.md；两份正式数据可分别用
  `OS_AGENT_MEMORY_BACKEND=memory|milvus` 重跑
