## 三、瓶颈定位（按实测）

1. **词面补召全量拉取 + O(N×M) 扫描（首要，规模下占 ≈92%）**：`orchestrator.recall`
   的 knowledge 词面补召走 `search(None, filters, top_k=10_000)` 拉取全部匹配的
   **完整记录**（含 content），再内存扫描 + merge + rerank。规模 1000 时该项
   ≈1740ms（milvus-lite 下标量 query 全量拉取更贵，≈526ms 重排段 + 更重的拉取）。
   与 TASK-006 阶段标记的 recall 词面路径风险一致，本次有了规模实测证据。
2. **CPU 语义编码（次要，串行占 44%，并发下争抢放大）**：BGE-M3 CPU 编码
   P50≈115-136ms；4 线程并发时争抢导致 P95 10924~15517ms。规模编码 1000 条
   148~180s（≈150-180ms/条）。
3. **milvus-lite 存储检索 167ms/次**：进程内 gRPC 往返 + keepalive 噪声
   （GOAWAY too_many_pings 日志），比进程内客户端慢 ~50 倍——单机轻量形态的固有开销。

**未达标差距如实呈现，不改金标、不放宽断言。** 优化方向（属 core/embedding 模块，
建议另开任务，本任务不越界修改）：
- 词面补召改造：投影裁剪（content 即可）/ 限制窗口 / 倒排索引化
- 查询编码缓存（可失效 LRU）或批处理；GPU / 轻量蒸馏模型
- 并发场景编码串行化（队列）避免争抢

## 四、附带修复（实测发现的产品级 bug）

`MilvusClient._ensure_collection`：**已存在的集合不 load**——milvus-lite（以及任何
重启后的 Milvus）集合处于 released 状态，直接 search 报 `code=101`。修复为
存在时也 `load_collection`（幂等）。持久化重启验证在新进程下通过（修复前必现）。

## 五、缺测与边界

- chat 耗时：模型服务不可用（503），**缺测单列**；配置可用服务后重跑即得
- 并发下未接入 GPU；`memory` 后端仅进程内对照，不代表 Milvus 部署形态
- hash 干跑（--allow-hash）仅验证 harness 接线，数字不代表语义
- rerank_profile 为近似口径（recall_total − encode − storage，含词面补召）
- 可复现命令见 WINDOWS.md「TASK-007 目标配置验收」；
  `python scripts/windows_perf_acceptance.py --scale 1000 --reps 10 --workers 4 --rounds 5`
